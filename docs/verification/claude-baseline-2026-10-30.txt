## Findings

**Release blockers (packaging and release tooling)**
1. **High: the source archive can include build output and stray files.** `tools/package.py:135-138` walks the folders on disk and only skips `.runs`, `__pycache__` and `.git`. I copied that exact logic into a test layout (`pkg-fixture-walk.txt`). It packed `tools/safety/core/target/…`, `tools/safety/inventory/target/…`, `vendor/*/target/…`, `core-fuzz/corpus/…`, `core-fuzz/artifacts/…` and an untracked notes file. On the real repo today it would also pack the untracked `docs/github-release-plan.md`.
   - The documented command at `docs/safety/m2-m5-handoff.md:110` creates `tools/safety/core/target` if `--target-dir` is left off.
   - Fix: build the file list from `git ls-files`, or archive with `git archive HEAD`, and refuse to run on a dirty tree.
2. **Medium: `.gitignore` misses the target folders of four nested crates.** It covers only the root, `core` and `core-fuzz` targets. `tools/safety/{components,fuzz,inventory,probes}/target` and `vendor/*/target` would show up as untracked files, risking an accidental commit, and would also be packaged.
3. **High: the packager accepts a weak verification summary.** `tools/package.py:31` only checks `passed: true`. But `tools/check.py:76-93` sets `passed` without the reference, stress or install checks (`reference_checks: 'Not requested'`). So a release can be packaged with no differential or clean-install evidence. The packager should require those steps and a minimum stress-round count.
4. **Medium: the source archive isn't tied to what was tested.**
   - The input fingerprint in `tools/check.py:29-37` leaves out `tests/`, `compat/cases/`, `compat/expected-*.json`, `docs/` and `spec/`.
   - Neither script records the git SHA or whether the tree was clean.
   - `package.py` never compares the fingerprint with the current tree. Only the binary and helper hashes are checked.
   - `tools/safety/baseline.py` already archives committed source and rebuilds it, so it is the better path for a release.
5. **Low: running `validate_spec.py` changes a tracked file.** `tools/safety/validate_spec.py:88` rewrites `spec/safety/validation.json` with a timestamp. Running the validator dirties the tree and changes a checked-in record. It should write to an output path that is passed in.
6. **Medium (process): `dist/` holds stale archives.** Their checksums verify, but the packaged `rless` is `8188fe99…`, not the current `271b12d7…`. The source archive has 148 files against 275 tracked now. It's ignored by git, but it must not be uploaded to a GitHub release. Regenerate from HEAD.
7. **Low:** `Cargo.toml` has no `repository` field. The README's description of the 809 results should say which run they come from.

**Longer-term safety work (not blockers for an experimental compatibility release that makes no safety claim)**
- M0 and M1 are still open:
  - Ownership review: 687 of 699 entries pending.
  - Silent EIO success: findings M0-IO-001 and M0-IO-002.
  - No ASan symbolizer and runtime bundle for glibc 2.41.
  - No formal independent native-invariant approval.
- The safe core isn't linked into the pager, and its fuzz runs give no credit toward the production fuzz budget.
- The main crate has only 9 Rust tests. Behavior coverage rests on the Python replay.
